# S6-08f: Shared Members & Links Panels

> **Parent:** B6-08 (Frontend — Hub Shell, Information Architecture & Navigation)  
> **Status:** `[ ]`  
> **Complexity:** 🟡 Medium  
> **Owner:** `frontend/src`

---

## Scope

Deliver the two hub-administration surfaces that are identical across all four hub types: `frontend/src/components/hubs/MembersPanel.tsx` and `frontend/src/components/hubs/HubLinksPanel.tsx`. Both render inside `HubShell` at the Members and Links tabs and read their permissions exclusively from `useHubPermissions()` — there is no per-type variant of either component.

The members panel manages hub membership and roles with last-owner protection. The links panel manages cross-hub consumption grants, enforcing the `hubs.md` §3.3 direction matrix in the target picker itself so an illegal pairing is never submittable, and warning about dependent resources before a revoke — since link validity is re-checked at execution time, revoking a link immediately breaks dependent agents, workflow nodes and eval targets.

## Actionables

- [ ] Create `frontend/src/components/hubs/MembersPanel.tsx` rendered at `routes.hubs.members(hubType, hubId)`.
  - [ ] Table columns: avatar + display name, email, hub role, invited by, joined date, row actions.
  - [ ] The hub `owner_id` row is marked with an `Owner` badge and sorted first; the current user's row is subtly highlighted.
  - [ ] Client-side search across name and email, plus a role filter.
- [ ] Implement "Add member" as an existing-user picker only — searching platform users by email/name — with an explicit note that inviting a brand-new person to the platform happens in `/admin/invites`, not here.
  - [ ] The role selector offers `maintainer`, `contributor`, `viewer`; `owner` is not assignable through this control.
  - [ ] Users already in the hub appear disabled in the picker with a "Already a member" caption.
- [ ] Implement inline role change via a per-row select, with an optimistic-free flow: the select is disabled during the request and reverts on failure with an error toast.
- [ ] Implement last-owner protection as a hard client-side rule mirroring the server:
  - [ ] The final `owner` cannot be demoted or removed; the control is disabled with the tooltip "A hub must always have at least one owner".
  - [ ] Transferring ownership is a separate, explicitly-labelled destructive action available only when `can("transfer_ownership")`, requiring typed confirmation of the hub name via [frontend/src/components/shared/ConfirmModal.tsx](frontend/src/components/shared/ConfirmModal.tsx), and warning that the current owner is demoted to `maintainer`.
  - [ ] Removing yourself warns that you will immediately lose access to the hub and will be redirected to `routes.hubs.directory()`.
- [ ] Create `frontend/src/components/hubs/HubLinksPanel.tsx` rendered at `routes.hubs.links(hubType, hubId)`, split into two clearly labelled sections.
  - [ ] **Outgoing** — hubs this hub consumes (this hub is `source_hub_id`); creatable and revocable here.
  - [ ] **Incoming** — hubs that consume this hub (this hub is `target_hub_id`); read-only, with a note that only the consuming hub's owners/maintainers can revoke.
- [ ] Encode the allowed direction matrix once as a shared constant used by both this panel and the S6-08e wizard.
  ```ts
  export const ALLOWED_LINK_TARGETS: Record<HubType, HubType[]> = {
    agent: ["ingestion"],
    workflow: ["agent", "ingestion"],
    eval: ["workflow", "agent"],
    ingestion: [], // ingestion hubs never consume another hub
  };
  ```
  - [ ] The create-link target picker lists only hubs whose type is in `ALLOWED_LINK_TARGETS[hub.hub_type]`; nothing may link into an `eval` hub, and links are never transitive — state this in the panel's helper copy.
  - [ ] Targets where the caller holds less than `contributor` are shown disabled with the reason, since link creation requires `owner`/`maintainer` on the source **and** at least `contributor` on the target.
  - [ ] When the matrix yields an empty list (ingestion hubs), render an explanatory empty state instead of a disabled picker.
- [ ] Render each outgoing link row with the target hub's icon/accent, name, `{type}/{slug}`, `access_level` badge (`read` vs `use` with a one-line meaning), creator and creation date, plus a direct navigation link into the target hub when the caller is a member of it.
- [ ] Implement revoke with a dependent-resource warning:
  - [ ] Before showing the confirm dialog, query the link's dependents and list them by name and kind — e.g. "3 agents bind collections from this hub", "1 workflow node instantiates an agent from this hub", "2 eval suites target resources in this hub".
  - [ ] State plainly that revoking takes effect immediately and that those dependents will begin failing with a link error at execution time.
  - [ ] Require typed confirmation of the target hub name when dependents exist; a plain confirm is sufficient when there are none.
- [ ] Role gating for both panels: with `can("manage_members")` / `can("manage_links")` false, the panels render as read-only tables with no add, edit, revoke or overflow controls rendered at all — a `viewer` and a `contributor` both see membership and links but no affordances.
  - [ ] When the hub is archived, controls render disabled with the "This hub is archived and is read-only" tooltip rather than being hidden, so owners can see what they would be able to do after unarchiving.
- [ ] Loading / empty / error expectations:
  - [ ] Both panels render table skeletons on first load and keep the previous rows visible during background refresh.
  - [ ] Empty states: "You are the only member of this hub" with an add action when permitted; "This hub does not consume any other hub yet" for outgoing links; "No other hub consumes this hub" for incoming links.
  - [ ] Mutation failures surface as inline row-level errors plus a toast, never as a silent no-op, and the affected row reverts to its server state.
  - [ ] A `403` on any mutation triggers a refetch of the hub context, since it implies the caller's role changed underneath them.
