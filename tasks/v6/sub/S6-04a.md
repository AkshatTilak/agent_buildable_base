# S6-04a: Hub-Scoped Collection Manager

> **Parent:** B6-04 (Ingestion Hub — Collections & Datastore Bindings)  
> **Status:** `[x]`  
> **Complexity:** 🟡 Medium  
> **Owner:** `projects/syntraflow`  

---

## Scope

Convert `projects/syntraflow/src/collections/manager.py` from a globally-flat, `tenant_id`-filtered
catalogue into a hub-scoped one. Today `CollectionManager.create_collection` takes `tenant_id="default"`,
enforces a **global** unique name, and uses the friendly name directly as the physical Qdrant collection
name. In V6 every method takes a required `hub_id`, names are unique per hub, and the physical store
name becomes `{hub_slug}__{collection_name}`.

This subtask also adds the per-collection retrieval strategy configuration that S6-04d consumes, and
the delete-safety rules that prevent a hub from destroying a populated collection by accident.

## Actionables

- [x] Extend `SyntraFlowCollection` in `projects/syntraflow/src/database/models.py`:
  - Add `hub_id = Column(String(36), ForeignKey("hubs.id", ondelete="CASCADE"), nullable=False, index=True)`.
  - Add `physical_name = Column(String(320), nullable=False, unique=True, index=True)`.
  - Add `retrieval_config_json = Column(JSON, nullable=False, default=dict)`.
  - Add `datastore_binding_id = Column(String(36), ForeignKey("datastore_bindings.id", ondelete="SET NULL"), nullable=True)`.
  - Drop `tenant_id`; replace the global unique on `name` with
    `__table_args__ = (UniqueConstraint("hub_id", "name", name="uq_collection_hub_name"),)`.
- [x] Add the physical-name helper to `manager.py` and use it everywhere a Qdrant/Neo4j name is needed:
  ```python
  _SLUG_RE = re.compile(r"[^a-z0-9_]+")

  def physical_collection_name(hub_slug: str, name: str) -> str:
      """Deterministic global name: '{hub_slug}__{collection_name}', both normalised."""
      return f"{_SLUG_RE.sub('_', hub_slug.lower())}__{_SLUG_RE.sub('_', name.lower())}"
  ```
  - Validate `name` against `^[a-zA-Z0-9][a-zA-Z0-9 _-]{0,62}$` and reject `__` in the friendly name so
    the separator stays unambiguous → `422`.
- [x] Change every `CollectionManager` method signature to take `hub_id` as the first keyword argument
      and include it in the `WHERE` clause, per `hubs.md` §5.3:
  - `create_collection(*, hub_id, name, embedding_model="jina-clip-v2", vector_dimension=1024, description=None, retrieval_config=None, datastore_binding_id=None)`
  - `list_collections(*, hub_id)` — remove the `tenant_id` parameter entirely.
  - `get_collection(*, hub_id, collection_id)` — resolve by id **or** name but always filtered by `hub_id`.
  - `delete_collection(*, hub_id, collection_id, force=False)`
  - `update_collection(*, hub_id, collection_id, description=None, retrieval_config=None, datastore_binding_id=None)`
  - Never accept a resource id alone: a lookup by primary key without `hub_id` is an IDOR bug.
- [x] Resolve `hub_slug` inside the manager by loading the `hubs` row for `hub_id` once per call
      (or accepting a `HubContext`), and raise `ValueError("Unknown hub")` → `404` when it is missing or
      `hub_type != "ingestion"`.
- [x] Rework `create_collection` transaction ordering so Postgres and Qdrant cannot diverge:
  - Check per-hub name uniqueness first → `409 {"detail": "Collection 'x' already exists in this hub"}`.
  - Create the Qdrant collection under `physical_name` via the client returned by
    `resolve_vector_client(hub_id)` (S6-04b) — **not** a bare `VectorClient()`.
  - Only then insert the SQL row; if the SQL insert fails, delete the just-created physical collection
    in a `finally` compensation block.
  - Replace the current swallowed `except Exception: logger.error(...)` around Qdrant creation with a
    raised `CollectionProvisioningError` — a silent partial create is not acceptable.
- [x] Persist and validate the per-collection retrieval strategy in `retrieval_config_json`:
  ```json
  {
    "strategy": "hybrid",          // dense | sparse | hybrid | graph
    "top_k": 5,
    "rrf_k": 60,
    "score_threshold": null,
    "graph_depth": 2
  }
  ```
  - Validate with a `CollectionRetrievalConfig` Pydantic model in
    `projects/syntraflow/src/collections/schemas.py`; unknown strategies → `422`.
  - Default to `{"strategy": settings.RAG_STRATEGY, "top_k": 5, "rrf_k": 60}` when omitted.
- [x] Implement delete safety in `delete_collection`:
  - Refuse with `409 {"detail": "Collection is not empty", "documents": n}` when
    `syntraflow_documents` rows reference it and `force` is `False`.
  - With `force=True`, cascade in order: delete Qdrant points/collection by `physical_name`, delete
    Neo4j nodes carrying the `hub_id` + `collection_id` properties, then delete the SQL rows.
  - Return a `{"deleted": {"documents": n, "chunks": n, "vectors": n}}` summary.
- [x] Update `list_collections` / `get_collection` output to expose `hub_id`, `name`, `physical_name`,
      `retrieval_config`, `datastore_binding_id` and `points_count`, and to drop `tenant_id`; keep the
      `status: "unreachable"` degradation when the vector store cannot be reached.
- [x] Migrate `CollectionManager` from the synchronous `sqlalchemy.orm.Session` to `AsyncSession`
      (`self.db.execute(select(...))` + `await`), matching the rest of the gateway, and update the
      callers in `projects/syntraflow/api.py` and `projects/syntraflow/src/api/`.
- [x] Add unit coverage in `tests/test_ingestion_hub.py` (created in S6-04f) asserting two different
      hubs can each own a collection named `policies` with distinct `physical_name` values and that a
      `get_collection` call with the wrong `hub_id` returns `None`.
